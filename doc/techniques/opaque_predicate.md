# 不透明谓词（Opaque Predicate）

> 往分支条件里塞一个恒真（或恒假）的判断，让"这个分支走不走"在静态层面不可判定。

| 项 | 值 |
|---|---|
| 对标术语 | jvmtp `obfuscation.opaque`；业界通称 opaque predicate |
| 作用层 | RegIR pass（`applyOpaquePredicates`） |
| 开关 | `--regc-obfuscate`（基础形态）/ `--regc-opaque-zero`（零恒等变体） |
| 后端 | RegC ✅ / LLVM ✅（超子集则整方法回退）/ StackC ❌ / VMC4 ❌ |
| 默认 | 关 |
| 状态 | ✅ 已落地 |

## 对抗什么

控制流恢复的第一步是判断"分支条件是否恒定"。不透明谓词制造的是**形式上有数据
依赖、实际上恒真**的条件：反编译器看到 `if (f(x))` 无法直接剪枝，要么保守地
保留两个分支（控制流图爆炸），要么先证明 `f(x)` 恒真（要算）。

## 机制

谓词被**合并进**已有的整型 / 布尔分支条件，而不是新插入一个裸 `if`——后者会
引入无对应源码的空块，反编译后很显眼。

`--regc-opaque-zero` 提供三种零 UB 的位运算恒等变体，按 `(seed, site)` 选：

| 变体 | 恒等式 | 说明 |
|---|---|---|
| demorgan | `~(~x) == x` | 双重取反 |
| shift-pair | 移位对消 | 左右移互为逆 |
| or-dec | 或/减恒等 | 补码代数恒等 |

"零 UB"是硬要求：带 UB 的恒等式在有符号溢出等边界上会被 UBSan / 编译器按 UB
处理，语义就不是恒等了。

## 产物形态

```c
// 变换前
if (r1 > r2) goto L1;

// 变换后（示意）
if (((r1 > r2) & (~~r3 == r3)) != 0) goto L1;
```

## 代价

| 维度 | 影响 |
|---|---|
| 性能 | 每分支多若干位运算；谓词本身的计算在运行时真实执行 |
| 产物体积 | 小幅膨胀 |
| 编译期 | 恒等式若被编译器证明恒真会被 DCE（与 CFF 死块不同，本项不刻意对抗 DCE） |

## 已知绕过面

- **符号执行**：谓词可判定，跑一遍就知道恒真。
- **编译器常量传播**：若谓词输入是编译期常量，会被直接折掉。变体选择掺 seed
  是为了避免同一形状反复出现被模式匹配，不是为了对抗求解。

## 与其他技术的关系

- 与 **CFF** 常被一起提起但机制不同：CFF 改控制流的**结构**（多跳 dispatcher），
  opaque 谓词改**条件的判定难度**。
- 与 **CFF 死块**配合：CFF 死块条件刻意依赖运行时 state 以抗 DCE，opaque 谓词
  不做这个。
