# 运行时反侦测检查点（Runtime Protection）

> 受保护方法入口注入检查点，检出调试器 / JVMTI agent 等侦测信号时按预设动作响应。

| 项 | 值 |
|---|---|
| 对标术语 | 业界通称 anti-debug / anti-tamper；本仓内称 runtime protection |
| 作用层 | 发射端（入口注入）+ 运行时（mj2x-rt `rt_protect` 模块） |
| 开关 | `--runtime-protection <动作>` / `--runtime-protection-step` / `--runtime-protection-delay <ms>` |
| 后端 | RegC ✅ / LLVM ✅ / VMC4 ✅ / StackC ❌ |
| 默认 | `none`（不注入） |
| 状态 | ✅ 已落地（PR #797） |

## 对抗什么

前面所有技术对抗的都是**静态分析**。运行时保护对抗的是**动态观察**：调试器
附加、JVMTI agent、动态 instrumentation、单步跟踪。

没有它，其余技术全部可以被"跑一遍看结果"绕过。

## 机制

受保护方法入口注入一个检查点调用。检查点按 `step` 概率触发（无调试器信号时约
`1/step` 触发率），命中即执行预设动作。

| 动作 | 行为 |
|---|---|
| `none` | 不注入（默认） |
| `log` | 记录 |
| `delay` | 睡眠 `delay_ms` 毫秒——拖慢分析节奏而非拒绝，不易被定位 |
| `fake` | 返回默认值——**行为静默偏离**，让 trace 结果不可信 |
| `terminate` | 终止 |

`fake` 是最有对抗价值的一档：不崩溃、不报错，只是结果不对。分析者拿到一份看起来
正常的 trace，结论却是错的——比 `terminate` 更难受，且不暴露检查点位置。

状态变量是**函数级全局**（`mj2x_rt_cp_N`），由编译管线附加的 `rt_protect` 源
提供；LLVM 侧编译时附带该源。

## 代价

| 维度 | 影响 |
|---|---|
| 性能 | 每方法入口一次调用；`step` 越大开销越小（概率触发） |
| 误伤 | **合法环境可能触发**。调试器、profiler、APM agent 都是侦测信号——`terminate` 档在用户环境里等于自毁 |
| 体感 | `delay` 档会真实拖慢生产环境 |

`terminate` 只在明确知道产物不会被合法调试时使用。

## 已知绕过面

- **检查点是可定位的**：入口的调用指令在产物里是明文，patch 掉即失效。
- **概率触发意味着可漏**：`step` 大时短运行可能一次都不触发。
- **只查已知信号面**：新型 instrumentation 不在检测列表里就不触发。

## 与其他技术的关系

- 与 **safe-env** 互补（一个查调试器，一个护 JNI 表）。
- 与 **VM 虚拟化的懒解密**同向：都在提高动态观察的成本。
- 与所有静态技术正交：这一项是唯一的动态面。
