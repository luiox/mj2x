# POD 类降级为 C struct（Object Scalar Replacement）

> 纯原生字段、不逃逸的 Java 类在 native 侧降级为 C struct：字段访问从每两次
> JNI 往返降为零，字段名也从产物里消失——struct 成员是偏移，不再有
> `GetIntField(obj, "x")` 这种直接暴露字段名与类型的调用。

| 项 | 值 |
|---|---|
| 对标术语 | 业界通称 scalar replacement / object inlining；JVM 侧对应 escape analysis + 标量替换 |
| 作用层 | 分析（逃逸分析）→ 发射端 |
| 开关 | `--regc-pod-struct` |
| 后端 | RegC 先试点（LLVM 侧未走这条路） |
| 默认 | 关 |
| 状态 | ✅ 已落地（PR #24） |

## 对抗什么

1. **性能**：字段访问是 `jfieldID` 缓存查找 + `Get/SetXxxField` 两次 JNI 往返
   （实例字段另加 null 检查）。struct 成员读写是零 JNI。
2. **可还原锚点**：`GetIntField(obj, "x")` 直接暴露字段名和类型。struct 成员是
   偏移，字段名从产物里消失。

## 降级条件（必须全部满足）

| 条件 | 理由 |
|---|---|
| 字段全是 primitive（Z/B/C/S/I/J/F/D），**无引用字段** | 引用字段涉及 GC 与写屏障，struct 表示不了 |
| 不实现接口、无子类 | 分派必须能静态绑定到声明类 |
| 对象不返回、不存进数组或字段 | 逃逸即失效 |
| 不传给任何外部方法 | 外部方法按 Java 对象语义访问 |
| 不 `hashCode` / `equals` / `toString` | 这三个是身份语义，struct 没有 |
| 不 `synchronized` | 对象头监视器语义 |
| 不当 `Object` 用（不向上转型） | 同上 |
| 非库类 | 库类的语义边界不由本编译单元控制 |

构造器要能识别成 struct 初始化：`NEW` + `INVOKESPECIAL <init>` 配对，且
`<init>` 体可静态分析。

## 机制

**逃逸分析复用现成底座，不从零写。** RegC 侧 StringBuilder / StringBuffer
native lowering 已有一套完整的形状：union-find 归并"根"（分配点 → 寄存器根）、
escape events 记录（参数传递、返回、存储即逃逸）、use-after-escape 判定（
逃逸后再用即整根回退）。POD 降级复用同一套判定——`RegIdUnionFind` 因此提到内部
共享头，两份副本必然漂移。

**别名是指针，不是值。** backing struct + 指针变量，边拷贝拷指针。

### 隐藏程度：做的是方案 (a)

| 方案 | 做法 | 状态 |
|---|---|---|
| (a) 字段挪进 native 内存，Java 侧类只剩空壳，getter 走 JNI 读 struct | 类定义保留，字段存储外移 | **已实现** |
| (b) 整个类从产物里删掉 | 类定义消失 | 未做 |

(b) 需要先把"这个类在编译输入之外没有被引用"证明出来，这个证明在 JAR 边界上
很难成立——反射、序列化、其他未受保护的代码都会崩。

## 两个只有实测才会暴露的坑

**1. 融合分配抢在 Allocate 前面。** `new X()` + `<init>()` 会被融合成 JNI
`NewObjectA`，POD 的 Allocate 分支永远拿不到它。不排除融合的话**降级覆盖面是零**
——功能写完但一个方法都不会命中，静态看不出来。

**2. 别名必须是指针，不能是值拷贝。** 初版按值拷贝 struct，产物快了 3.15x 但
**结果是错的**（`840438784 ≠ 1693116032`）——同一个对象在 RegIR 里可以有多个
寄存器（phi / 边拷贝），值拷贝让它们变成互不影响的副本，与 Java 引用语义不等价。
改成指针别名后结果正确，且比错误版本更快。

这类"快但算错"的 bug 静态看不出来，只能靠样本比对 JVM 输出。

## 代价

| 维度 | 影响 |
|---|---|
| 覆盖面 | 条件极严，实际命中率低（大多数类都有 `toString` 或向上转型） |
| 正确性风险 | 逃逸分析漏判 = 数据静默错乱，比崩溃更难查 |
| 反射 | 反射访问 struct 化对象拿到的是空壳，语义与未保护版本不一致 |

### 实测（PodBench，字段访问密集样本）

jvm-obf-tester 里没有这种形状（它的 probe 都调 JDK 方法，字段访问占比低），
测不出差异，故单独造了样本：热点循环内反复读写同类对象的原生字段。

| | 耗时 | 结果 |
|---|---|---|
| JVM 基线 | 2.08ms | 1693116032 |
| mj2x 关 | 611ms | 1693116032 |
| **mj2x 开** | **103ms** | **1693116032** |

5.9x。仍比 JVM 慢 50x——JVM 自己会做逃逸分析与标量替换，这个样本正是它的主场；
本项的价值在于把 mj2x 自身的字段访问开销从 JNI 降到零，不是跟 JVM 比。

## 已知绕过面

- **反射仍能看到字段声明**（方案 (a) 的固有限制），序列化可能读到空值。
- **覆盖面是硬上限**：降级条件每一条都是硬门槛，真实代码里大量类会因
  `toString` / 向上转型被拒。这是安全换收益的取舍，不是实现缺陷。

## 验证

- PodBench 三方对照，结果与 JVM 基线逐位一致
- jvm-obf-tester 全量 13 项 probe Passed（开关打开状态下）
- RegCTest 新增 4 项（默认关无 struct 痕迹 / 命名 / 库类拒绝 / 降级判定边界）
- 全量回归 860 tests

## 与其他技术的关系

- 与 **native→native 直调**是同族的结构降级：一个消除字段访问的 JNI 边界，
  一个消除调用的 JNI 边界。
- 与**立即数隐藏**可叠：字段名消失 + 常量值消失。
- 与 VM 虚拟化**互斥**：VMC4 不走 RegIR 变换（分工决定见
  [vm_virtualization.md](vm_virtualization.md)）。
